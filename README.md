# PowerBridge · Phase 1

A schema-first Power Apps data migration workbench. PostgreSQL owns platform state and business data. A separate NestJS worker validates CSV files and publishes through COPY staging. Next.js provides the administrator/operator UI. Apache Superset is an independent analytics application.

Power Apps remains the operational source. This project does not implement forms, approvals, live or bidirectional synchronization.

## Start locally

Prerequisites: Node 22.12+, Corepack, Docker with Compose, and available ports 3000, 3001, 5432 and optionally 8088.

```sh
cp .env.example .env
# Edit .env: set distinct database/reporting passwords and secrets.
# Generate SECRET_ENCRYPTION_KEY with: openssl rand -hex 32
# Generate SUPERSET_SECRET_KEY with: openssl rand -hex 48
corepack enable
pnpm install --frozen-lockfile
pnpm build
docker compose up --build -d postgres redis migrate api worker web
```

Create your first administrator explicitly; there are no seeded passwords:

```sh
docker compose exec -e ADMIN_EMAIL=admin@example.test -e ADMIN_PASSWORD='your-long-unique-password' api pnpm --filter @platform/api seed
```

Open http://localhost:3000 and API documentation at http://localhost:3001/api/docs. The initial Departments dataset is synthetic and must pass **Check Schema Availability** before importing. See [local development](docs/local-development.md) for running processes outside containers.

```sh
docker compose --profile analytics up --build -d superset superset-register
```

Superset runs at http://localhost:8088 with its separately configured credentials. It has its own metadata database (`superset_meta` role) and permissions. `superset-register` adds the read-only reporting connection, the approved reporting views and clearly labelled SYNTHETIC example charts through the Superset REST API.

## Workflow

Upload CSV → inspect deterministic profile → edit a manual or assisted proposal → approve → copy/download developer artifacts → developer reviews and deploys repository migrations → check schema → map and validate all rows → publish → browse records and reporting views.

Approval does not execute DDL. The in-application assistant receives bounded metadata and optional masked samples; it has no repository, filesystem, shell, DDL, or deployment tools. Proposed code is generated by application-owned templates.

## Development and checks

```sh
pnpm typecheck
pnpm test
pnpm lint
pnpm test:e2e
sh scripts/verification/release-gate.test.sh
```

Database integration tests require an isolated `TEST_DATABASE_URL` (role needs CREATEDB) and `TEST_REDIS_URL`. Never point them at operational data. Full service tests also need Redis. See [verification results](docs/verification.md) for exactly what was run and remaining limits.
